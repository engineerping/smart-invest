当微服务链路变长、规模变大时，K8s 集群就会变成一个黑盒。如果一个订单请求失败了，它到底是在 `gateway`、`order-service` 还是 `payment-service` 挂掉的？是因为 JVM 频繁 Full GC，还是因为 K8s 宿主机 CPU 被打满了？

为了解决这个问题，在 K8s 体系中，通常会采用“两翼齐飞”的架构策略：

1. **SkyWalking（分布式链路追踪）：** 解决 **Trace（线）** 的问题。追踪单次请求在微服务间的流转。
2. **Prometheus + Grafana（多维指标监控）：** 解决 **Metric（面）** 的问题。监控 K8s 节点、Pod 容器以及 JVM 的健康状态。

作为资深 Java 开发，你不需要为了监控去重构代码。K8s 强大的“旁路解耦”能力可以让这些监控组件像外挂一样无缝接入。

## 一、 SkyWalking 在 K8s 中的“无感外挂”艺术

在传统物理机时代，你要用 SkyWalking，得在启动 JAR 包时手动加上参数 `-javaagent:/path/to/skywalking-agent.jar`。

但在 K8s 中，Pod 是动态销毁和创建的，我们不可能把 Agent 预先写死在每个 Java 业务镜像里，更不可能手动去每台机器上粘文件。K8s 提供了一种极其优雅的解法：**Init Container（初始化容器）+ 共享目录**。

### 1. 核心原理：偷偷换件衣服

K8s 的 Pod 允许配置一种特殊的容器叫 `Init Container`。它会在你的 Java 容器启动之前先启动，跑完就销毁。

* 我们把 SkyWalking 官方的 Agent 镜像作为 Init Container。
* 启动时，Init Container 把自己的 `skywalking-agent.jar` 复制到一个 Pod 内部的**共享临时目录**（`emptyDir`）中。
* 随后，Java 容器启动，因为它和 Init Container 共享了这个目录，Java 进程就可以直接通过环境变量读取并加载这个 Agent。

### 2. 生产级 YAML 落地

看看在 Deployment 中如何实现这一“神操作”，你的 Java 基础镜像不需要做任何改动：

```yaml
spec:
  template:
    spec:
      # 1. 初始化容器：专门用来运送 SkyWalking Agent 
      initContainers:
        - name: sw-agent-sidecar
          image: apache/skywalking-java-agent:8.12.0-java17 # 官方 Agent 镜像
          command: ['sh', '-c', 'cp -r /skywalking/agent/* /target/agent']
          volumeMounts:
            - name: sw-agent-volume
              mountPath: /target/agent

      containers:
        - name: java-order-container
          image: myregistry.com/mall/order-service:v1.2.0
          
          # 2. 注入 JVM 启动参数，直接读取共享目录里的 Agent
          env:
            - name: JAVA_TOOL_OPTIONS
              value: "-javaagent:/opt/sw/agent/skywalking-java-agent.jar"
            - name: SW_AGENT_NAME
              value: "order-service" # 在 SkyWalking 界面上显示的名字
            - name: SW_AGENT_COLLECTOR_BACKEND_SERVICES
              value: "skywalking-oap.monitoring.svc.cluster.local:11800" # 连上 K8s 内部的 SW 服务
          
          volumeMounts:
            - name: sw-agent-volume
              mountPath: /opt/sw/agent # 挂载共享目录

      # 3. 声明 Pod 内部共享的内存/磁盘目录
      volumes:
        - name: sw-agent-volume
          emptyDir: {}

```

**Java 工程师的爽点：** 业务开发人员甚至不需要知道 SkyWalking 的存在，运维通过一套通用的 K8s 模板，就能让所有 Java 应用自动具备分布式链路追踪能力。

## 二、 Prometheus + Grafana：如何监控“全家桶”

Prometheus 是目前 K8s 的御用监控神工。它的核心工作模式是 **Pull（拉取）**：它会每隔 15 秒，主动去调用各个组件的 HTTP 接口，把监控指标抓取回来，存入自己的时序数据库。

在长链路下，Prometheus 实现了 **基础设施、容器、JVM 三层合一** 的立体监控。

### 1. 第一层：基础设施与 Node 监控

Prometheus 会在每台机器上通过 **DaemonSet** 部署一个叫 `Node Exporter` 的小程序。它负责把宿主机的 CPU、内存、磁盘 I/O、网络流量转成 Prometheus 认识的指标。

### 2. 第二层：K8s 容器与 Pod 监控

K8s 的每台机器上管理容器的系统组件（`kubelet`），内置了一个叫 `cAdvisor` 的功能。它能实时监控每个 Java Pod 容器被分配了多少资源，实际用了多少，有没有触发前面我们提到的 `OOMKilled`。

### 3. 第三层：Java 应用内部监控 (JVM & Spring Boot)

作为 Java 开发，我们要让 Prometheus 看到 JVM 内部的 GC 次数、堆内存使用、线程池活跃数，需要用到 **Spring Boot Actuator + Micrometer**。

* **第一步：** 在 Java 项目的 `pom.xml` 中引入依赖：
```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>

```


* **第二步：** 在 `application.yml` 中暴露端点：
```yaml
management:
  endpoints:
    web:
      exposure:
        include: 'prometheus' # 暴露 /actuator/prometheus

```



启动后，访问该接口，你会看到一堆密密麻麻的形如 `jvm_gc_pause_seconds_count` 的文本。

### 4. 闭环：Prometheus 是怎么自动找到这些 Java Pod 的？

集群里有成百上千个 Pod，IP 天天在变，Prometheus 怎么知道去哪拉取这些 JVM 指标？
依靠 **K8s 的服务发现**。你只需要在 Java 的 Service 部署文件里加上几个神奇的 **Annotations（注解）**：

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
  annotations:
    prometheus.io/scrape: "true"         # 告诉 Prometheus：来抓我！
    prometheus.io/path: "/actuator/prometheus" # 抓取的接口路径
    prometheus.io/port: "8080"           # 抓取的端口

```

Prometheus 会定期扫描 K8s 的 Service，一旦看到带有 `prometheus.io/scrape: "true"` 的 Service，就会自动把它们加入到自己的抓取清单中，Pod 扩容到 100 个，它就能自动抓 100 个。

最终，这些数据会被倒进 **Grafana**。在 Grafana 炫酷的仪表盘上，你可以清晰地在同一个时间轴上看到：**618 零点流量暴涨 $\rightarrow$ 容器 CPU 冲高 $\rightarrow$ JVM 触发 Full GC $\rightarrow$ SkyWalking 链路上订单接口响应延迟从 50ms 飙升至 2s**。至此，全链路彻底透明。

## 三、 终极大厂架构：Service Mesh（服务网格）趋势

如果你觉得上面在每个 Java 应用里引入 Micrometer、修改 YAML 注入 SkyWalking 还是有点繁琐，业界大厂（如字节、蚂蚁）目前正在全面铺开 **Service Mesh（以 Istio 为代表）**。

* **终极解法：** K8s 会在你的 Pod 里自动塞入一个叫 **Envoy (Sidecar)** 的网络代理容器。
* 所有的流量进出你的 Java 容器，必须先经过 Envoy。
* Envoy 在网络底层直接把 Trace ID 注入 HTTP Header，直接把网络延迟、吞吐量等指标上报给 Prometheus 和 SkyWalking。
* **结果：** 你的 Java 代码不需要引入任何监控依赖，YAML 也不需要配置 Init Container，真正做到了 **0 代码侵入、0 配置侵入** 的全链路监控。

* **Prometheus** 利用 K8s 的 **Service 注解声明** 实现了动态的服务指标发现，将 JVM、容器、物理机指标融为一体。
