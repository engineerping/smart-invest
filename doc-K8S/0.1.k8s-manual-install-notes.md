# 从 K3S 到手动安装 K8S —— 学习笔记

> 日期：2026-08-02
> 背景：本机 (georgeserver, Ubuntu 24.04, 192.168.31.192) 用一条命令装好了 k3s。
> 本文对照 k3s 自动完成的工作，梳理"如果手动安装等价的原生 Kubernetes，需要做哪些事"。

---

## 0. 一句话理解 k3s 与 k8s 的关系

Kubernetes（k8s）是平台本身，由一组独立组件组成；
k3s 是 Rancher 出的 k8s 发行版（CNCF 认证），把原生 k8s 的多个组件**打成一个单二进制**，去掉云厂商特性，用**内嵌 sqlite 代替 etcd**、用**内嵌 containerd**、用**flannel** 做网络，并预置了常用插件。

所以在 k3s 上只需要装一个 `k3s` 二进制 + 一条 systemd 服务；
在原生 k8s 上，这些工作是**分组件、分步骤**完成的。

## 1. 本机 k3s 安装后的实际状态（快照）

> 下面是 2026-08-02 从本机抓取的真实状态，作为对照基准。

### 1.1 运行中的进程

```
/usr/local/bin/k3s server          ← 一个进程，内含所有控制面组件 + kubelet
└── containerd                     ← k3s 内嵌的容器运行时（子进程）
```

另外还独立运行着 Docker 的 containerd + dockerd（之前手动装的，互不干扰）。

### 1.2 监听端口（对照组件）

| 端口 | 组件 | 说明 |
|------|------|------|
| 6443 | kube-apiserver | k8s API 入口（HTTPS），所有客户端都访问它 |
| 10250 | kubelet | 每台节点上的 agent，供 apiserver 调用来管理 Pod |
| 10257 | kube-controller-manager | 控制器（健康检查绑定回环地址） |
| 10259 | kube-scheduler | 调度器（健康检查绑定回环地址） |
| 10248 | kubelet | healthz 健康检查 |
| 10249 | kube-proxy | metrics 端口 |
| 10256 | kube-proxy | healthz（回环） |

> 原生 k8s 中，这些**是不同的进程**，各有各的 systemd 服务（或静态 Pod）。

### 1.3 数据目录

```
/etc/rancher/k3s/k3s.yaml            ← kubeconfig（集群访问凭据）
/var/lib/rancher/k3s/
├── server/
│   ├── tls/                         ← 所有证书（CA、apiserver、kubelet 等）
│   ├── token / node-token           ← 节点加入集群的令牌
│   ├── agent-token                  ← agent 模式令牌
│   ├── db/  +  kine.sock            ← k3s 用 kine 把 etcd(Editable Text Configuration-Distributed) 换成 sqlite（单节点默认）
│   ├── manifests/                   ← 自动部署清单（traefik、local-path 等）
│   ├── static/                      ← static Pod 目录
│   └── cred/  etc/  ...             ← 各组件凭据/配置
├── agent/                           ← kubelet / containerd 工作目录
└── data/                            ← k3s 版本数据
```

### 1.4 命名空间

```
default          kube-node-lease     kube-public        kube-system
```

（原生 k8s 也是这四个基础命名空间。）

### 1.5 k3s 自动装好的插件（对照表）

| k3s 自动部署 | 对应原生 k8s 里需要手动装的东西 |
|---|---|
| CoreDNS | 集群内 DNS（Service 名解析） |
| Traefik（Ingress 控制器） | 需要自己选装 nginx-ingress / traefik 等 |
| metrics-server | `kubectl top` 需要它提供 CPU/内存指标 |
| local-path-provisioner | 动态 PV 存储（容器数据落本地盘） |
| flannel（CNI） | 需要自己选装 flannel / calico / cilium 等网络插件 |
| ServiceLB（klipper-lb） | 需要自己配置 LoadBalancer 方案 |

> 注意：快照时这些插件 Pod 都处于 `ContainerCreating`，因为要从 Docker Hub 拉镜像超时（后面第 6 节专门讲）。

## 2. 原生 k8s 的组件架构（先建立全景图）

一条 `curl ... | sh` 背后，k3s 悄悄完成了全部组件的部署。手动装 k8s 时，你要逐个认识它们：

```
                    ┌──────────────────── 控制面 (Control Plane) ────────────────────┐
                    │                                                                │
  客户端(kubectl)──►│  kube-apiserver :6443                                          │
                    │     │                  ┌──► kube-controller-manager :10257     │
                    │     │                  │         （各种控制器循环）             │
                    │     │  调度+状态        ├──► kube-scheduler :10259              │
                    │     │                  │         （给新 Pod 挑节点）            │
                    │     ▼                  └──► etcd（集群数据存储，原生 k8s 用）   │
                    │  所有组件都只信任 apiserver，并通过它读写集群状态                │
                    └───────────────────────────────────────────────────────────────┘
                                    │ 网络 (flannel/calico...)
                    ┌────────────────┴─────────────────┐
                    ▼                                  ▼
             Worker Node                           Worker Node
             kubelet :10250  ◄──── watch/调度指令 ────┘
             kube-proxy（iptables/ipvs 做转发）
             containerd（拉镜像、起容器）
```

**关键理解**：
1. **一切走 apiserver**。controller-manager、scheduler、kubelet、kubectl 都只和 apiserver 对话，谁也不直接跟 etcd 说话（除 apiserver 外）。
2. **控制面组件可以以"静态 Pod"形式跑**——kubelet 直接读 `/etc/kubernetes/manifests/` 目录拉起它们，这是 `kubeadm` 的默认方式。
3. **集群数据存在 etcd**（k3s 单节点默认换成 sqlite/kine）。

## 3. 对照表：k3s 自动做的事 vs 手动装 k8s 要做的事

| # | k3s 自动完成 | 手动安装原生 k8s 时你需要做                                                               |
|---|---|--------------------------------------------------------------------------------|

| 5 | 装好 kube-apiserver | 部署 kube-apiserver（静态 Pod + 配置文件）                                               |
| 6 | 装好 kube-controller-manager | 部署 kube-controller-manager                                                     |
| 7 | 装好 kube-scheduler | 部署 kube-scheduler                                                              |
| 8 | 装好 kubelet + containerd | 安装并启动 kubelet，注册节点到集群                                                          |
| 9 | 装好 kube-proxy | 部署 kube-proxy（DaemonSet）                                                       |
| 10 | 配好 flannel CNI | 安装网络插件（flannel / calico / cilium 选一）                                           |
| 11 | 写好 kubeconfig（/etc/rancher/k3s/k3s.yaml） | 生成并配置 admin kubeconfig（`~/.kube/config`）                                       |
| 12 | 装 CoreDNS | 安装 CoreDNS（Deployment + Service）                                               |
| 13 | 装 metrics-server | 安装 metrics-server（HPA / `kubectl top` 依赖）                                      |
| 14 | 装 Traefik Ingress | 安装 Ingress 控制器（nginx-ingress 等）                                                |
| 15 | 装 local-path-provisioner | 配置 StorageClass（本地卷、NFS、Longhorn 等）                                            |
| 16 | 提供 systemd 服务 + 开机自启 | 为 kubelet/containerd 配 systemd unit；控制面用静态 Pod 由 kubelet 拉起                    |
| 17 | 一条命令加入 worker | `kubeadm join <apiserver>:6443 --token ... --discovery-token-ca-cert-hash ...` |
| 18 | 升级/卸载脚本 | 手动维护各组件版本，`kubeadm upgrade` 管理                                                 |

## 4. 手动安装等价 K8s 的完整步骤（实践篇）

> 以最主流的 `kubeadm` 方式为例，单控制面 + 多 worker 的等价拓扑。

### 4.0 前置条件（每台机器）

```bash
# 1. 关闭 swap（kubelet 默认要求）
sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab

# 2. 加载内核模块
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay
sudo modprobe br_netfilter

# 3. 内核参数（桥接流量走 iptables）
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system
```

### 4.1 安装容器运行时 containerd

```bash
# 以 Docker 源里的 containerd 为例
sudo apt-get update
sudo apt-get install -y containerd.io

# 生成默认配置，并打开 systemd cgroup 驱动（k8s 要求，不然节点报错）
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

# 国内可追加镜像加速（sandbox/pause 镜像拉取等）
#   在 config.toml 的 [plugins."io.containerd.grpc.v1.cri".registry.mirrors] 下
#   配置 https://docker.m.daocloud.io 等镜像

sudo systemctl restart containerd
sudo systemctl enable containerd
```

### 4.2 安装 kubeadm / kubelet / kubectl

```bash
# 添加 k8s apt 源（阿里云镜像）
curl -fsSL https://mirrors.aliyun.com/kubernetes/apt/doc/apt-key.gpg | sudo apt-key add -
echo "deb https://mirrors.aliyun.com/kubernetes/apt/ kubernetes-xenial main"   | sudo tee /etc/apt/sources.list.d/kubernetes.list

sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
# 固定版本，避免自动升级
sudo apt-mark hold kubelet kubeadm kubectl
```

### 4.3 初始化控制面（仅控制面节点）

```bash
# 提前拉镜像（可选，加速后续）
sudo kubeadm config images pull --image-repository registry.aliyuncs.com/google_containers

# 初始化
sudo kubeadm init   --image-repository registry.aliyuncs.com/google_containers   --pod-network-cidr=10.244.0.0/16   --apiserver-advertise-address=192.168.31.192

# 按提示配置 kubectl
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

# 记录输出的 join 命令（worker 加集群要用）
```

`kubeadm init` 自动完成了对照表中 3~9 的所有事：
- 生成 CA 和全部证书（`/etc/kubernetes/pki/`）
- 生成 admin kubeconfig
- 以**静态 Pod** 方式部署 apiserver / controller-manager / scheduler / etcd（清单在 `/etc/kubernetes/manifests/`）
- 下发 bootstrap token

### 4.4 安装网络插件（CNI）

```bash
# 选一个即可。flannel 需要 pod-network-cidr=10.244.0.0/16 对应
kubectl apply -f https://raw.githubusercontent.com/flannel-io/flannel/master/Documentation/kube-flannel.yml

# 或者 Calico：
# kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/master/manifests/calico.yaml
```

### 4.5 安装核心插件

```bash
# CoreDNS（kubeadm 一般已装，确认即可）
kubectl get pods -n kube-system | grep coredns

# metrics-server（可选但推荐）
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Ingress 控制器（二选一）
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.12.0/deploy/static/provider/baremetal/deploy.yaml

# 本地动态存储（等价 k3s 的 local-path-provisioner）
kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/master/deploy/local-path-storage.yaml
```

### 4.6 加入 worker 节点

```bash
# 在每台 worker 上执行（来自 kubeadm init 输出的 join 命令）
sudo kubeadm join 192.168.31.192:6443 --token <token>   --discovery-token-ca-cert-hash sha256:<hash>

# 控制面查看节点
kubectl get nodes
```

### 4.7 验证（对照 k3s 快照里的验证点）

```bash
kubectl get nodes -o wide          # 状态 Ready，角色 control-plane/worker
kubectl get pods -A                # 所有组件 Running
kubectl get ns                     # 四个基础命名空间
ss -tlnp | grep -E '6443|10250'    # 关键端口
```

## 5. 组件逐一说明（为什么 k3s 不用你管，手动就得管）

| 组件 | 职责 | k3s 里 | 原生 k8s 里 |
|---|---|---|---|
| kube-apiserver | 所有 API 请求的唯一入口，认证/授权/准入 | 内嵌在 k3s 二进制 | 静态 Pod 或二进制 |
| kube-controller-manager | 循环控制器：Node、ReplicaSet、Deployment、Endpoint 等 | 内嵌 | 静态 Pod |
| kube-scheduler | 为待调度 Pod 挑选合适节点 | 内嵌 | 静态 Pod |
| etcd | 集群状态存储（KV） | 默认用 kine+sqlite（省内存） | 独立 etcd 集群（`/etc/kubernetes/manifests/etcd.yaml`） |
| kubelet | 节点 Agent：拉起/销毁 Pod、上报状态 | 内嵌 | 独立 systemd 服务 |
| kube-proxy | 维护 Service 的 iptables/IPVS 规则 | 内嵌（DaemonSet） | DaemonSet |
| containerd | 容器运行时：拉镜像、管理容器 | 内嵌（k3s 子进程） | 独立 systemd 服务 |
| CNI | 容器网络（Pod IP、跨节点互通） | 内置 flannel | 手动安装 flannel/calico/cilium |
| CoreDNS | 集群内 DNS | 自动部署 | 手动安装 |
| metrics-server | `kubectl top` / HPA 的数据源 | 自动部署 | 手动安装 |
| Ingress 控制器 | 域名→Service 的七层入口 | 自动装 Traefik | 手动装 nginx-ingress 等 |
| StorageClass | 动态分配持久卷 | 自动装 local-path | 手动配置 |

**核心心得**：k3s 把"控制面组件 + 运行时 + 插件"全塞进一个二进制和一个 systemd 服务；原生 k8s 把这些拆成十几个进程和部署清单，每一样都要装、配、管。

## 6. 本次快照发现的问题（重要实践教训）

快照显示：控制面是 Ready 的，但 `coredns`、`metrics-server`、`traefik`、`local-path-provisioner` 全部卡在 `ContainerCreating`。

原因（日志可见）：
```
failed to pull image "rancher/mirrored-pause:3.6":
failed to resolve reference "docker.io/rancher/mirrored-pause:3.6":
dial tcp 108.160.166.57:443: i/o timeout
```

即：**这些镜像要从 Docker Hub (`registry-1.docker.io`) 拉取，本机访问超时**（网络环境原因）。

结论与教训：
1. **k3s 能装、节点能 Ready，不代表组件就绪**——插件镜像还要能拉下来。
2. 手动装 k8s 同样会遇到（甚至更麻烦）：`kubeadm config images pull` 如果拉不动，整个 init 会失败。
3. 解决思路（任选）：
   - 给 containerd 配置国内镜像加速（见 4.1 节末尾）
   - 提前手动 `ctr images pull` / `crictl pull` 需要的镜像
   - 对 k3s：设置 `INSTALL_K3S_MIRROR=cn`（装的时候已用，但插件镜像仍走 Docker Hub）
   - 对 kubeadm：`--image-repository registry.aliyuncs.com/google_containers`
   - 如果实在拉不动 pause 镜像，可在 containerd 里单独给 docker.io 配 mirror
4. 修复命令（k3s 场景，先排查再看是否配置加速后再重启）：
   ```bash
   sudo crictl pull rancher/mirrored-pause:3.6   # 测试能否拉到
   sudo systemctl restart k3s                     # 重启触发重试
   kubectl get pods -A                            # 再观察
   ```

## 9. 实战修复：组件镜像拉取失败（2026-08-02）

### 现象

k3s 装好后节点 Ready，但 kube-system 的 coredns、metrics-server、traefik、local-path-provisioner 全部卡在 `ContainerCreating`。

### 根因

```
failed to pull image "rancher/mirrored-pause:3.6":
failed to resolve "docker.io/rancher/mirrored-pause:3.6":
dial tcp ...:443: i/o timeout
```

这台机器（华硕，WiFi）到 **Docker Hub 官方源的 blob 下载被限速到 0.5~3 KB/s**。测试结论：
- Cloudflare 直连可达 2.5 MB/s —— 说明带宽本身没问题，是 Docker Hub 线路被限速
- 多个国内镜像加速源（1panel/daocloud/ustc/163...）要么失效要么同样龟速
- 唯一例外：**很小的镜像（301KB 的 pause）能拉下来**，几十 MB 的就卡死

### 解决思路：本地拉取 + 内网传输 + 手动导入

利用"另一台网络快的机器"绕开受限线路：

```
[快网机器]  crane pull (amd64 镜像)  →  打包 tar
      │  内网传输 (本地实测 5~50 MB/s)
      ▼
[华硕]  k3s ctr images import --label io.cri-containerd.image=managed xxx.tar
```

关键命令：

```bash
# 1. 在快网机器上拉 amd64 镜像（crane 单二进制，无需 Docker）
crane pull --platform linux/amd64 --format tarball \
  docker.io/rancher/mirrored-coredns-coredns:1.14.4 coredns.tar

# 2. 传过去后，用 k3s 的 ctr 导入（注意必须用 k3s 自己的 socket）
sudo k3s ctr --address=/run/k3s/containerd/containerd.sock \
  --namespace=k8s.io images import coredns.tar

# 3. 验证
sudo k3s ctr --address=/run/k3s/containerd/containerd.sock \
  --namespace=k8s.io images list
```

### 关键坑：镜像必须带 managed 标签

直接 `ctr images import` 导入的镜像，在 `crictl images` 里能看到，但 kubelet 拉 Pod 镜像时**仍然会走网络**。原因：

k3s 的 containerd 开启了 `use_local_image_pull = true`，但它只对带 `io.cri-containerd.image=managed` 标签的镜像使用本地副本。官方拉下来的镜像自带这个标签，手动导入的没有。

**修复**：给导入的镜像补标签后重启 k3s / 重建 Pod：

```bash
sudo k3s ctr --address=/run/k3s/containerd/containerd.sock \
  --namespace=k8s.io images label \
  docker.io/rancher/mirrored-coredns-coredns:1.14.4 \
  io.cri-containerd.image=managed

# 删除卡住的 Pod 让它们用本地镜像重建
sudo k3s kubectl delete pods -n kube-system --all --force --grace-period=0
```

### 修复后验证

```

## 10. 云托管 K8S vs 传统自建 vs k3s 单节点：控制平面的三种形态（2026-08-02）

### 你的问题：云服务商的 K8S 是不是只提供了 IaaS worker node？

**理解完全正确。** 以阿里云 ACK、AWS EKS、Google GKE 为例：

- **控制平面（Control Plane / Master）** 运行在云厂商自己的基础设施上。你付钱，它负责高可用、升级、etcd 备份。你根本看不到、也 SSH 不进控制平面的机器。
- **你只是用 IaaS（ECS / EC2 / Compute Engine）创建 Worker Node**，它们通过网络加入这个云端控制平面，实际跑你的 Pod。你为 Worker Node 的算力付费（按虚拟机规格），为控制平面付管理费（或按集群规格）。

### 那我们这台华硕呢？

**这台华硕上的 k3s 是单节点、全功能集群。** 所有控制平面组件和你的应用 Pod 全部跑在同一台机器上。

```

### 关键区别对照

| 维度 | 传统自建 K8S | 云托管 K8S | k3s 单节点 |
|------|-------------|-----------|-----------|
| 控制平面位置 | 你的物理机/VM | 云厂商托管（不可见） | 和 worker 同一台机器 |
| etcd / 存储 | etcd 集群(3-5节点) | 云厂商托管 etcd | kine + SQLite（单文件） |
| 控制平面高可用 | 你手动配置多台 | 云厂商保证 SLA | 无（单节点） |
| 二进制体积 | ~200MB+ (每个组件独立) | 你不需要装 | ~60MB（全部打包） |
| 最少机器数 | 2台 (1 CP + 1 worker, 不推荐) | 1台 worker（控制平面云托管） | **1台** |
| 运维负担 | 高（证书轮换、etcd 备份、版本升级全手动） | 低（控制平面免运维） | **极低**（一个二进制，systemctl 管启停） |
| 适用场景 | 大型生产集群 | 生产集群（企业首选） | 边缘计算 / 家庭实验室 / 开发环境 |

### 为什么 k3s 能把控制平面和 worker 合在一起？

k3s 做了一系列"瘦身"来让这件事可行：

1. **kine 替代 etcd**：etcd 是分布式 KV 存储，需要 3~5 节点保证一致性，资源消耗大。kine 把 Kubernetes 的存储接口翻译成 SQL 语句，后端用 SQLite（或 MySQL/Postgres），单文件、零运维。
2. **去掉云厂商相关的 controller**：k3s 去掉了大量 `--cloud-provider` 相关的代码（约 100 万行），体积大幅缩小。
3. **内嵌 containerd + runc**：不需要额外安装容器运行时，k3s 自带 containerd。
4. **内嵌 flannel**：网络插件直接编译进去了。

所以一台机器、一个 60MB 二进制，就能跑一个完整的 Kubernetes 集群。这就是为什么我们说 k3s 是"轻量级 K8S 发行版"——它轻掉的不是你的 Pod 调度能力（标准的 Kubernetes API 一个不少），而是运维基础设施的复杂性。
