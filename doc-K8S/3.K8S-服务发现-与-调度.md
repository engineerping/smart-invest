微服务之间的“服务发现（Service Discovery）”**和**“智能调度（Scheduling）”，可以说是 K8s 能够统治云原生领域的两大家族绝活。

对于资深 Java 开发而言，你可能非常熟悉 Spring Cloud 体系中的 **Eureka/Nacos + Ribbon/Feign**。在进入 K8s 世界后，你会发现：**K8s 在基础设施层直接把这些功能给“侵入式”地干掉了**。

我们分两部分，用你最熟悉的微服务视角来拆解 K8s 的底层魔术。

---

## 第一部分：K8s 的“服务发现”机制

在 Spring Cloud 中，服务发现的逻辑是：`order-service` 启动时把自己的 IP 注册到 Nacos，`user-service` 调用时先去 Nacos 拉取 IP 列表，然后自己在本地通过 Ribbon 做负载均衡。

但在 K8s 中，**你不需要在 Java 代码里引入任何 Nacos SDK 或 Feign 客户端**。K8s 利用 **DNS + CoreDNS + kube-proxy** 实现了一套对代码完全透明的服务发现。

### 1. 核心幕后功臣：CoreDNS（域名解析）

当你创建一个名为 `order-service` 的 Service 时，K8s 内部的 DNS 组件（CoreDNS）会自动在集群内注册一条专属域名：
`order-service.prod.svc.cluster.local`

在你的 `user-service`（Java 应用）中，当你想调用订单服务，你的 `RestTemplate` 或 `WebClient` 直接写：

```text
http://order-service:8080/api/order

```

K8s 的容器底层会自动把 `order-service` 这个短域名解析为该 Service 的 **Cluster IP**（虚拟 IP）。

### 2. 流量分发利器：kube-proxy（负载均衡）

Cluster IP 是一个虚拟 IP，真实的物理网卡上根本不存在这个 IP。那么流量是怎么过去呢？

* 每台 Node（服务器）上都跑着一个叫 **kube-proxy** 的系统进程。
* 它是真正的底层交警。它会实时盯着 API Server，一旦发现 `order-service` 背后挂了 3 个新 Pod，它就会在宿主机的 Linux 内核里修改 **IPVS** 或 **iptables** 转发规则。
* 当你的 Java 请求发送到 Cluster IP 时，Linux 内核在网络层（甚至没出机器）直接把这个虚拟 IP 替换成了某一个真实健康的 **Pod IP**。

**Java 工程师的爽点：** 你不需要再维护 Eureka/Nacos 服务器，不需要担心 Java 客户端本地缓存的实例列表过期。K8s 在网络底层帮你把负载均衡和健康检查全部做掉了，你的 Java 代码回归到了最纯粹的 HTTP/gRPC 调用。

## 第二部分：K8s 的“智能调度”机制

调度（Scheduling）解决的是另一个问题：**当你有 100 台服务器（Nodes），你提交了一个 Java Pod，K8s 凭什么决定把它放到哪一台机器上？**

负责这个核心大脑工作的是 **kube-scheduler（调度器）**。它的调度过程就像是高考录取，分为两个严格的阶段：**过滤（Predicates）** 和 **评分（Priorities）**。

### 阶段一：过滤（硬性指标筛选）

调度器会逐一检查集群里的所有 Node，把不符合条件的机器直接“无情刷掉”。常见的硬性规则有：

* **资源是否足够（PodFitsResources）：** 你的 Java Pod 声明了 `requests.memory: 4Gi`，那剩余空闲内存小于 4G 的 Node 直接淘汰。
* **端口是否冲突（PodFitsHostPorts）：** 容器如果写死了想占用宿主机的 8080 端口，而某台 Node 的 8080 已经被占了，淘汰。
* **节点亲和性（NodeAffinity）：** 你在 YAML 里指定了“这个应用必须跑在带 SSD 硬盘的服务器上”，没有 SSD 的 Node 淘汰。

### 阶段二：评分（优中选优）

经过第一轮过滤后，可能还剩下 5 台 Node 满足条件。接下来调度器会对它们进行打分（0-100分），分数最高的获胜。评分策略非常智能：

* **资源最优化（LeastRequestedPriority）：** 哪台机器目前空闲的 CPU 和内存最多，得分就越高（倾向于平均分配，避免旱涝不保收）。
* **平衡性（BalancedResourceAllocation）：** 倾向于选择 CPU 和内存消耗比例最平衡的机器（比如不希望某台机器内存爆满而 CPU 空闲）。
* **打散原则（SelectorSpreadPriority）：** 如果你要求部署 3 个副本。为了高可用，调度器会极力避免把它们放在同一台宿主机甚至同一个机架上。如果它们分布在不同的 Node 上，得分就高。

最终，分数最高的 Node 胜出，调度器把结果写回数据库，该 Node 上的组件（kubelet）就会收到命令：“来活了，快把这个 Java 镜像拉起来！”

## 三、 高级调度技巧：如何控制 K8s 的大脑？

作为技术专家，你不能甘心让 K8s 盲目调度。你可以通过 YAML 文件来“操控”调度器的意志。有三种最常用的高级手段：

### 1. 亲和性 (Affinity)

* **Node 亲和性：** “我的订单服务需要极高的 I/O，请把它调度到有 `disk=ssd` 标签的机器上。”
* **Pod 亲和性：** “我的网关服务（Ingress Pod）和授权服务（Auth Pod）天天大量通信，请尽量把它们调度在**同一个 Node** 上，走本地环回网络，别走跨机器网络。”

### 2. 反亲和性 (Anti-Affinity)

* “我是大促的核心‘支付服务’，为了绝对的高可用，不允许任何两个支付 Pod 呆在同一台机器上。万一某台机器冒烟了，我还有别的机器在撑着。”

### 3. 污点 (Taints) 与 容忍 (Tolerations)

这是非常形象的一个概念：

* **污点 (Taint)：** Node 可以对自己说：“我有污点，我很臭（比如这台服务器是昂贵的 GPU 专机，或者专门跑数据库的）。”普通的 Pod 只要一靠近，就会被调度器弹开。
* **容忍 (Toleration)：** 除非你在你的 Java Pod YAML 里写明：“我能容忍这个污点”。调度器才会把你放过去。这实现了**特定独占资源**的完美隔离。

---

### 总结

* **服务发现：** K8s 依靠 **CoreDNS** 做域名解析，依靠 **kube-proxy** 在 Linux 内核层做第四层负载均衡，取代了传统的 Java 微服务注册中心。
* **智能调度：** K8s 依靠 **kube-scheduler** 经历“过滤 + 打分”的算法，并在你提供 `Affinity` 或 `Taints` 的意志下，将 Pod 完美安插在最合适的机器上。

理清了服务发现与调度的底层之后，你的 K8s 理论版图基本全部拼凑完成了。
