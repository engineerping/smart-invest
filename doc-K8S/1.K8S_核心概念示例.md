为了让你对 K8S 拥有全局的、专家级的理解，我们直接拉一张“K8S 核心概念全景表”，把绝大多数常用概念一网打尽，并划分为不同的职责领域。

最后，我们用一个“大型 618 电商大促”的极简史诗级案例，把这些概念全部串联起来。

---

## 一、 K8S 核心概念大阅兵

我们可以把 K8S 的概念分为四大类：**计算与调度、网络与接入、配置与存储、管理与隔离**。

### 1. 计算与调度（核心工作负载）

* **Pod**：K8S 最小的运行单元，里面包裹着具体的容器（如你的 Java 进程）。
* **Deployment**：管理**无状态**应用（如 Spring Boot 服务）。负责滚动更新、弹性伸缩。
* **StatefulSet**：管理**有状态**应用（如 MySQL、Redis）。它能保证 Pod 有固定的名字、固定的存储绑定和启动顺序。
* **DaemonSet**：在集群的**每一台机器**上都必须跑一个的 Pod。通常用于日志收集（Logstash）或系统监控。
* **Job / CronJob**：一次性任务 / 定时任务（如每天凌晨 2 点生成对账单）。

### 2. 网络与接入（通信枢纽）

* **Service**：内网负载均衡。给一组 Pod 提供一个永恒不变的内网 IP 和域名。
* **Ingress**：外网流量网关（类似 Nginx）。负责把公网的 HTTP/HTTPS 请求路由到内部的 Service 上。
* **NetworkPolicy**：网络防火墙。控制哪些 Pod 之间可以互相访问，哪些不能。

### 3. 配置与存储（数据外挂）

* **ConfigMap**：非敏感配置中心（如 `application.yml`）。
* **Secret**：敏感配置中心（如数据库密码、密钥、SSL 证书）。
* **PersistentVolume (PV)**：真实的存储资源（比如一块 AWS 的云硬盘，或者网盘）。
* **PersistentVolumeClaim (PVC)**：Pod 发出的“存储申请单”。Pod 说：“我要 10G 空间”，K8S 就会自动去找匹配的 PV 绑定。

### 4. 资源与隔离（物理边界）

* **Node**：真正干活的物理机或虚拟机。
* **Namespace**：逻辑隔离边界（如 `dev`、`test`、`prod` 环境）。
* **ResourceQuota**：资源限额。规定某个 Namespace 最多只能用多少 CPU 和内存，防止某个坏应用把整台机器撑爆。

## 二、 史诗级案例：一个“微服务电商系统”的 618 蜕变

为了把上面**所有概念**串起来，我们来模拟一个真实的 Java 微服务电商系统，在 `prod`（生产环境）**Namespace** 下的运作过程：

### 1. 稳健的日常：系统初始化

你的电商系统包含“订单服务”（无状态）和“MySQL 数据库”（有状态）。

* **ConfigMap** 存着订单服务的 `logging.level=INFO`；**Secret** 密文存着 MySQL 的密码。
* 你通过 **Deployment** 部署了 3 个“订单服务”的 **Pod**，它们通过环境变量把 ConfigMap 和 Secret 的配置读进 JVM。
* 因为数据库不能丢数据，你通过 **StatefulSet** 部署了 MySQL 的 **Pod**。MySQL 提交了一个 500G 的 **PVC** 申请，K8S 自动分配了一块高并发的 **PV**（云硬盘）挂载给它。
* 为了让订单服务能找到数据库，你创建了一个名为 `mysql-service` 的 **Service**；为了让前端能访问订单服务，你创建了一个名为 `order-service` 的 **Service**。
* 集群大门处，**Ingress** 守在那里，配置了规则：只要用户访问 `https://mall.com/api/order`，流量就转给 `order-service`。
* 每台 **Node**（服务器）上，**DaemonSet** 都在默默运行，把所有 Pod 打印出来的 `logback.xml` 日志实时抽走到公司的日志中心。

### 2. 惊心动魄的 618：大促来临

618 零点，流量瞬间暴涨 100 倍！

* **Deployment** 收到警报，触发自动扩容，瞬间把订单服务的 **Pod** 从 3 个克隆到了 50 个，分布在不同的 **Node** 上。
* 由于 **Service** 内部负载均衡的存在，它立刻感知到了这 50 个新 Pod 的加入，把汹涌的流量均匀地分发给它们，Java 应用顶住了压力！
* 为了防止黑客攻击或开发人员写错代码导致安全漏洞，**NetworkPolicy** 发挥了作用：它规定，只有“订单服务”的 Pod 允许访问 `mysql-service`，其他任何服务的 Pod（比如前端、活动页面）如果试图直接连接数据库，直接一枪干掉。
* 由于流量太大，某个 Node 节点的内存被 Java 的堆内存占满了。幸好你设置了 **ResourceQuota** 和 Pod 的资源限制，K8S 发现该节点濒临崩溃前，果断在其他空闲的 Node 上重启了受影响的 Pod，完成了自愈，用户甚至没有感到卡顿。

### 3. 凌晨 2 点的余晖：收尾工作

大促狂欢结束，到了清算时间。

* **CronJob** 被准时唤醒，它拉起了一个临时 **Pod**。这个 Pod 连上数据库，把今天的订单数据全部导出、对账，然后把报表发送到财务邮箱。
* 任务完成后，这个 CronJob 的 Pod 自动销毁，释放出宝贵的 CPU 和内存资源。

---

### 总结：

你看，K8S 就像一个**高度自动化的智慧工厂**：

* **Pod** 是车间里的工人，**Container** 是工人手里的工具。
* **Deployment/StatefulSet** 是车间主管，盯着工人数量。
* **Service/Ingress** 是传送带和导流员，负责把原材料（流量）送进来。
* **ConfigMap/Secret/PV** 是仓库，负责提供图纸和原材料。

下面是一个**企业级、全配置的 Java 微服务（Spring Boot）部署 YAML 配置文件**。它把我们前面聊到的 **Deployment、Service、Ingress、ConfigMap、Secret、PVC 以及健康检查（探针）** 全都串联在了一起。

在 K8s 中，我们通常把这些配置写在一个 `.yaml` 文件里，通过一个横杠 `---` 来分隔不同的资源对象。你可以像读 Java 的 `pom.xml` 或 `application.yml` 一样来阅读它：

```yaml
# ========================================================================
# 1. 配置中心 (ConfigMap)：存放非敏感的 application.yml 配置
# ========================================================================
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-service-config
  namespace: prod
data:
  # 这里直接嵌入了 Spring Boot 的配置
  application.yml: |
    server:
      port: 8080
    logging:
      level:
        com.mall.order: INFO
    spring:
      datasource:
        url: jdbc:mysql://mysql-service.prod.svc.cluster.local:3306/order_db?useSSL=false

---
# ========================================================================
# 2. 密码箱 (Secret)：存放敏感信息（如数据库密码），内容必须经过 Base64 编码
# ========================================================================
apiVersion: v1
kind: Secret
metadata:
  name: order-service-secret
  namespace: prod
type: Opaque
data:
  # "Password123" 的 Base64 编码结果
  DB_PASSWORD: UGFzc3dvcmQxMjM=

---
# ========================================================================
# 3. 存储申请单 (PVC)：为 Java 日志申请一个 10Gi 的持久化云盘空间
# ========================================================================
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: order-log-pvc
  namespace: prod
spec:
  accessModes:
    - ReadWriteOnce # 这块盘只能同时被一个 Node 挂载进行读写
  resources:
    requests:
      storage: 10Gi # 申请 10GB 空间

---
# ========================================================================
# 4. 核心工作负载 (Deployment)：管理 Java 容器的副本数、镜像和高可用
# ========================================================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service-deployment
  namespace: prod
spec:
  replicas: 3 # 618 大促日常维持 3 个 Pod 副本（高可用）
  selector:
    matchLabels:
      app: order-service-app # 告诉 Deployment 它要管理带有什么标签的 Pod
  template:
    metadata:
      labels:
        app: order-service-app # 给 Pod 打上标签，方便被 Service 识别
    spec:
      containers:
        - name: java-order-container
          image: myregistry.com/mall/order-service:v1.2.0 # 你的 Spring Boot 镜像地址
          ports:
            - containerPort: 8080 # 容器内 Java 应用监听的端口
          
          # 【核心】把 ConfigMap 和 Secret 的值注入到 JVM 的环境变量中
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: "prod"
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: order-service-secret
                  key: DB_PASSWORD
                  
          # 【资源限额】防止 Java 堆内存堆积导致整台宿主机崩溃 (ResourceQuota 落地)
          resources:
            requests:
              memory: "1Gi"
              cpu: "500m" # 最少分配 0.5 核 CPU
            limits:
              memory: "2Gi" # 最多允许用到 2GB 内存，超过就会被 K8s 执行 OOM 杀掉重启
              cpu: "1000m"
          
          # 【健康检查】对接 Spring Boot Actuator
          # 存活探针：检查 Java 进程是否死锁或假死
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 30 # 刚启动时给 JVM 30秒的预热时间，不进行检查
            periodSeconds: 10
          # 就绪探针：检查 Java 是否完成了类加载和连接池初始化，能否开始接流量
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 20
            periodSeconds: 10

          # 【文件挂载】把前面申请的 10G PVC 挂载到容器内的日志目录
          volumeMounts:
            - name: log-volume
              mountPath: /app/logs # 你的 logback.xml 输出日志的路径
      
      # 声明这个 Pod 使用上面定义的 PVC
      volumes:
        - name: log-volume
          persistentVolumeClaim:
            claimName: order-log-pvc

---
# ========================================================================
# 5. 内部负载均衡 (Service)：给那 3 个 Java Pod 提供一个永恒不变的内网访问入口
# ========================================================================
apiVersion: v1
kind: Service
metadata:
  name: order-service # 其他微服务在集群内直接访问 http://order-service:8080 即可
  namespace: prod
spec:
  ports:
    - port: 8080       # Service 暴露的端口
      targetPort: 8080 # 对应 Pod 容器内的端口
  selector:
    app: order-service-app # 【关键】Service 通过这个标签，自动发现上面 Deployment 创建的 3 个 Pod

---
# ========================================================================
# 6. 集群大门 (Ingress)：反向代理，将公网流量路由进 Service
# ========================================================================
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mall-ingress
  namespace: prod
  annotations:
    kubernetes.io/ingress.class: "nginx" # 使用 Nginx 作为 Ingress 控制器
spec:
  rules:
    - host: api.mall.com # 只有访问这个域名的流量才进来
      http:
        paths:
          - path: /api/order # 匹配路径
            pathType: Prefix
            backend:
              service:
                name: order-service # 将流量转发给上面定义的 Service
                port:
                  number: 8080

```

### 作为 Java 开发，如何快速读懂这个 YAML 文件的精髓？

1. **配置是怎么进到 Java 里的？**
   在 Deployment 的 `env` 部分，我们用 `valueFrom` 关联了 Secret。当这个容器启动时，K8s 会自动在 Linux 操作系统中注入一个名叫 `SPRING_DATASOURCE_PASSWORD` 的环境变量。Spring Boot 默认的宽松绑定机制会自动把它识别并填入 `spring.datasource.password` 中，完全不需要改动 Java 代码！
2. **Spring Boot 的健康检查有多重要？**
   注意里面的 `livenessProbe` 和 `readinessProbe`。如果你的 Java 应用因为 Full GC 导致假死（进程还在，但无法响应请求），K8s 会通过 `livenessProbe` 发现并自动 **重启容器**；如果应用正在启动还没加载完，`readinessProbe` 会阻止流量进来，避免用户看到 502 报错。
3. **微服务之间怎么调用？**
   在 ConfigMap 里的数据库 URL 中，你看到了 `mysql-service.prod.svc.cluster.local`。这是 K8s 内部的 DNS 域名。你不需要知道 MySQL 的具体 IP，直接像访问外网域名一样访问这个 Service 名字，K8s 会在内网自动做负载均衡。

当你把这个 YAML 文件保存为 `order-service.yaml`，然后在服务器上执行一行命令：

```bash
kubectl apply -f order-service.yaml

```

K8s 就会瞬间开辟环境、挂载云盘、加载密钥、启动 3 个 Spring Boot 实例，并把公网网关配置好。
