在真实的生产环境中，将 Java（Spring Boot）代码通过 CI/CD 工具（以 GitLab CI 或 Jenkins 为例）自动化打包并部署到 K8s，是云原生开发中最核心的“黄金管道”。

这个流程的核心思想是：**“代码变更触发流水线，自动化产出镜像，‘声明式’更新 K8s 终态”**。

下面为你拆解一套业界大厂标准的、基于 **GitLab CI** 的云原生流水线架构和核心配置文件。

---

## 一、 云原生 CI/CD 的标准六驾马车（流程图解）

一个完整的 Java 自动化发布流程，通常包含以下 6 个阶段（Stage）：

1. **开发者提交代码：** 往 GitLab 提交代码（如 `main` 分支或打一个 Git Tag `v1.2.5`）。
2. **代码编译（Build）：** 运行 `mvn clean package`，生成 `jar` 包。
3. **镜像构建（Docker Build）：** 读取 `Dockerfile`，将 `jar` 包打包成 Docker 镜像。
4. **镜像推送（Push）：** 将镜像推送到企业私有镜像仓库（如 Harbor、AWS ECR 或阿里云 ACR）。
5. **配置清单修改（Manifest Update）：** 自动修改 `deployment.yaml` 文件中的镜像版本号。
6. **K8s 部署（Deploy）：** CI/CD 机器人调用 `kubectl apply`，K8s 触发滚动更新，优雅替换旧 Pod。

## 二、 核心资产一：Java 应用的 `Dockerfile`

在你的项目根目录下，首先需要准备一个精简、安全的 `Dockerfile`。推荐使用 **多阶段构建（Multi-stage Build）**，这样最终的镜像里不会包含 Maven 依赖和源码，体积能缩小 80%。

```dockerfile
# ---- 第一阶段：利用 Maven 镜像进行代码编译 ----
FROM maven:3.8.5-openjdk-17 AS builder
WORKDIR /app
# 巧妙利用 Docker 缓存：先复制 pom.xml 下载依赖（只要 pom 不变，这一步就不会重复执行）
COPY pom.xml .
RUN mvn dependency:go-offline

# 复制源码并打包
COPY src ./src
RUN mvn clean package -DskipTests

# ---- 第二阶段：构建极简的 Java 运行环境 ----
FROM openjdk:17-slim
WORKDIR /app

# 从第一阶段的成果物中，只把打包好的 jar 包拷过来
COPY --from=builder /app/target/order-service-*.jar ./app.jar

# 声明端口
EXPOSE 8080

# 启动命令（配合我们之前学的 K8s 百分比内存参数）
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -XX:InitialRAMPercentage=75.0 -XX:MaxRAMPercentage=75.0 -jar app.jar"]

```

## 三、 核心资产二：GitLab CI 流水线配置文件 (`.gitlab-ci.yml`)

在项目根目录下创建 `.gitlab-ci.yml`。GitLab Runner 看到这个文件就会自动跑自动化流程。

*(为了让逻辑更清晰，这里演示最核心的：打包、打镜像、发 K8s 三个阶段)*

```yaml
stages:
  - build-jar
  - build-image
  - deploy-k8s

variables:
  # 私有镜像仓库地址和镜像名
  REGISTRY_URL: "myregistry.com"
  IMAGE_NAME: "myregistry.com/mall/order-service"
  # 获取当前 Git 提交的短 Hash 作为版本号（如 e4a1b2c）
  VERSION: $CI_COMMIT_SHORT_SHA

# ----------------------------------------------------
# 1. 编译阶段：生成 JAR 包并作为成果物传给下一阶段
# ----------------------------------------------------
maven-build:
  stage: build-jar
  image: maven:3.8.5-openjdk-17
  script:
    - mvn clean package -DskipTests
  artifacts:
    expire_in: 1 mos
    paths:
      - target/*.jar # 将编译出来的 jar 暂存，供下一个阶段使用

# ----------------------------------------------------
# 2. 镜像构建与推送阶段
# ----------------------------------------------------
docker-build:
  stage: build-image
  image: docker:20.10.16 # 使用 Docker 镜像来运行 docker 指令
  services:
    - docker:20.10.16-dind # 开启 Docker-in-Docker 服务
  script:
    - echo "登录私有镜像仓库..."
    - echo "$REGISTRY_PASSWORD" | docker login -u "$REGISTRY_USER" --password-stdin $REGISTRY_URL
    - echo "开始构建 Docker 镜像，版本号为: $VERSION"
    - docker build -t $IMAGE_NAME:$VERSION .
    - echo "推送到仓库..."
    - docker push $IMAGE_NAME:$VERSION

# ----------------------------------------------------
# 3. K8s 部署阶段（自动更新 Deployment）
# ----------------------------------------------------
k8s-deploy:
  stage: deploy-k8s
  image: bitnami/kubectl:latest # 使用自带 kubectl 工具的镜像
  script:
    # 第一步：配置与 K8s 集群的连接认证（通常在 GitLab 的 Variables 里配置好 KUBECONFIG 凭证）
    - mkdir -p ~/.kube
    - echo "$KUBECONFIG_DATA" | base64 -d > ~/.kube/config
    
    # 第二步【核心魔术】：动态修改 K8s 部署文件中的镜像 Tag
    # 业界常用 sed 命令，把之前 yaml 里写的占位符（或者旧版本号）直接替换为当前最新的 Git Hash 变量
    - sed -i "s|image: myregistry.com/mall/order-service:.*|image: $IMAGE_NAME:$VERSION|g" k8s/deployment.yaml
    
    # 第三步：声明式应用更新
    - echo "正在向 K8s 集群应用最新的配置清单..."
    - kubectl apply -f k8s/deployment.yaml
    
    # 第四步：金标监控——等待滚动更新安全完成（如果失败，流水线会报错报错提示）
    - kubectl rollout status deployment/order-service-deployment -n prod --timeout=2m
  only:
    - main # 限制只有 main 分支的代码变动才会触发部署

```

## 四、 资深开发必须懂的 CI/CD 闭环设计

看了上面的 YAML 配置文件，你作为资深开发可能会产生以下几个极具深度的问题：

### 1. 为什么不需要自动更新 Service？

你在问题中提到“自动更新 K8s 上的 Service 和 Deployment”。其实在真实的 CI/CD 中，**我们几乎从来不更新 Service**。
因为 Service 的职责只是做负载均衡和提供一个固定域名（例如 `order-service`），它的配置（如端口、Label 选择器）是一成不变的。
我们真正更新的**只有 Deployment 里的 `image` 版本号**。当 Deployment 的镜像升级后，新 Pod 启动并带上了相同的 Label，Service 就会**自动**通过标签发现新 Pod，并把流量引过去。

### 2. 滚动更新（Rollout）时，Java 应用是怎么做到无感替换的？

K8s 在收到 `kubectl apply` 更新了镜像后，会按照以下逻辑进行**滚动更新**：

* 启动一个新镜像的 `Pod-New`。
* 等待 `Pod-New` 的 `readinessProbe`（就绪探针）通过（即你的 Spring Boot 已经完全初始化好，具备接流能力）。
* 将新流量引入 `Pod-New`。
* 触发我们上一课学的 `preStop` 钩子，让旧的 `Pod-Old` 优雅停机、断流，最后销毁。
  整个过程新老交替，在公网上看，没有丢掉任何一个请求。

### 3. 更高级的架构趋势：GitOps (ArgoCD)

上面演示的是 **“Push 模式”**（由 GitLab 直接越权去操纵 K8s）。大厂现在更流行 **“Pull 模式” (GitOps)**：

* 你的代码仓库只管打镜像。
* 另外有一个专门存放 K8s YAML 文件的配置仓库。
* 集群里装一个 **ArgoCD** 组件。ArgoCD 默默盯着配置仓库，一旦发现里面的 `deployment.yaml` 镜像版本变了，ArgoCD 就在 K8s 内部自己把自己更新了。这样安全性更高，CI 工具不需要拿 K8s 的最高控制权限。
