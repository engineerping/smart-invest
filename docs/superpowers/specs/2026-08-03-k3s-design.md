## 0. 决策摘要（与用户的头脑风暴结论）

| 决策点 | 结论 |
|---|---|
| 微服务拆分 | 4 个 SpringBoot 服务：user / fund / order / notification-worker + api-gateway + frontend |
| 服务间通信 | 同步 REST（K8S Service DNS 服务发现）+ RabbitMQ 异步（order→notification） |
| 数据库 | Postgres 16 独立跑在宿主机 Docker（不进 K3S） |
| 消息队列 | RabbitMQ 通过 Helm 部署进 K3S，带 Prometheus exporter 监控 |
| 前端 | React + Vite 现有代码，构建为 nginx 静态镜像，容器化进 K3S |
| IaC 技术栈 | **Helm + Kustomize 为主**（匹配用户新工作）；**Terraform 管 K3S 版作为学习资料** |
| Chart 组织 | monorepo 内**每服务一个独立 chart** + **umbrella chart** 聚合，Helm dependencies 走 `file://` 相对路径，无需额外仓库 |
| 镜像分发 | 构建后推 Docker Hub 公开仓库，K3S 拉取 |
| CI/CD | GitHub Actions 全自动：push → 构建 → 推镜像 → SSH 到服务器 helm upgrade |
| 监控 | Prometheus + Grafana（Helm 部署），微服务暴露 `/actuator/prometheus`，RabbitMQ exporter |
| 公网访问 | Traefik Ingress 入口 + 内网穿透软件映射公网域名 |
| 服务器 | 8GB 物理内存，JVM 堆受限（-Xmx512m 级），监控栈精简 |
| 演示场景 | ① 完整业务闭环 ② K8S 弹性自愈 ③ CI/CD 一键部署 ④ 监控指标 |

## 1. 目标架构

原图是 AWS EKS 生产版。本设计保留微服务形态与核心中间件，用自托管组件替换 AWS 专有服务：

```
公网 (内网穿透 frp/nps) → ASUS-Ubuntu:80/443
                                  │
                          ┌───────▼────────┐
                          │ Traefik Ingress │   ← K3S 自带
                          └───────┬────────┘
     ┌───────────────┬───────────┴──────────┬───────────────┐
     ▼               ▼                      ▼               ▼
 frontend         api-gateway          user-service    fund-service
 nginx 静态        SpringBoot           SpringBoot      SpringBoot
                    │  8080                 │               │
                    │  └───────┬────────────┘               │
                    │          ▼                            │
                    │    order-service (SpringBoot)         │
                    │          │                             │
                    │          │ ──RabbitMQ──▶ notification-worker
                    ▼          ▼                             ▼
               ┌───────────────────────────────────────────────┐
               │ Postgres 16 (宿主机 Docker, 不进 K3S)           │
               └───────────────────────────────────────────────┘
```

### 组件清单

| 组件 | 运行位置 | 端口 | 说明 |
|---|---|---|---|
| Traefik Ingress | K3S (自带) | 80/443 | 入口路由 |
| api-gateway | K3S | 8080 | SpringCloud Gateway 或自定义转发，统一入口/认证 |
| user-service | K3S | 8081 | 注册/登录/JWT/用户/风险测评 |
| fund-service | K3S | 8082 | 基金列表/净值/持仓/组合 |
| order-service | K3S | 8083 | 申购/赎回/订单查询，生产 MQ 消息 |
| notification-worker | K3S | 8084 | 消费 MQ，生成通知记录 |
| frontend | K3S | 80 | React 静态，nginx 托管 |
| Postgres 16 | 宿主机 Docker | 5432 | 唯一数据库 |
| RabbitMQ | K3S (Helm) | 5672/15672 | 消息队列，order→notification 解耦 |
| Prometheus | K3S (Helm) | 9090 | 指标采集 |
| Grafana | K3S (Helm) | 3000 | 可视化，预置面板 |

## 2. 代码拆分

### 2.1 Maven 结构（monorepo）

现有代码是模块化单体（8 个 module 聚合成一个 jar）。重写为**多服务独立可部署**：

```
backend/
├── pom.xml                     # 父 POM，统一依赖版本管理
├── common/                     # 共享库：JWT、异常处理、审计、DB 配置
├── user-service/               # ← module-user 迁移
├── fund-service/               # ← module-fund + module-portfolio + module-holding 合并
├── order-service/              # ← module-order + module-plan + module-scheduler 合并
└── notification-worker/        # ← module-notification 改造
```

- 每个服务 = 独立 Maven module + 独立 `main` + 独立 Dockerfile + 独立 Helm chart
- 通过 Maven `<parent>` 继承统一版本
- 服务间通过 REST + K8S Service DNS 互调（例如 order-service → http://user-service:8081）

### 2.2 各服务职责

| 服务 | 职责 | 主要依赖 |
|---|---|---|
| user-service | 注册/登录、JWT 签发与校验、用户资料、风险测评 | common, JPA, security, jjwt |
| fund-service | 基金列表/详情/净值走势、持仓、投资组合 | common, JPA, jjwt(client) |
| order-service | 申购/赎回、订单状态机、发布 MQ 消息 | common, JPA, jjwt, rabbitmq |
| notification-worker | 消费 MQ 订单事件、写通知记录 | common, JPA, rabbitmq |
| api-gateway | 路由转发到各服务、CORS、统一前缀 | gateway |

### 2.3 API 路由约定（api-gateway → 服务）

| 路径 | 目标服务 |
|---|---|
| `/api/auth/**` `/api/users/**` `/api/risk/**` | user-service |
| `/api/funds/**` `/api/portfolios/**` `/api/holdings/**` | fund-service |
| `/api/orders/**` | order-service |
| `/api/notifications/**` | notification-worker |

## 3. 数据与中间件

### 3.1 PostgreSQL（宿主机 Docker，不进 K3S）

- 镜像 `postgres:16-alpine`，卷持久化在宿主机
- 数据库名 `smartinvest`，用户 `smartadmin`（沿用现有 docker-compose 配置）
- K3S 内服务通过 `ExternalName Service` 或 ConfigMap 配置宿主机 IP 访问
- Flyway 保留现有 20 个迁移脚本（V1–V20）自动建表

### 3.2 RabbitMQ（进 K3S，Helm 部署）

- 使用官方 `rabbitmq` chart 或自定义 chart，含 `rabbitmq-prometheus` 插件
- 声明 queue/exchange：`order.events`（direct exchange → notification queue）
- order-service 生产，notification-worker 消费，消费失败重试+死信

### 3.3 密钥管理（K3S 原生）

- 数据库密码、JWT 密钥、RabbitMQ 密码 → K8S **Secret**
- 非敏感配置（URL、开关）→ ConfigMap
- 面试可讲：K8S Secret/ConfigMap 与 AWS Secrets Manager 的对应关系

### 4.1 Helm chart 设计（每服务独立 + umbrella）

```
charts/user-service/
├── Chart.yaml          # apiVersion/version/appVersion
├── values.yaml         # replicaCount/image/resources/env/probes
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml  # 非敏感配置
    ├── secret.yaml     # 引用已有 Secret（不硬编码）
    ├── hpa.yaml        # 可选，演示 HPA
    ├── serviceaccount.yaml
    └── _helpers.tpl    # 命名模板：name/fullname/labels
```

umbrella 聚合：

```yaml
# umbrella/Chart.yaml
apiVersion: v2
name: smart-invest
type: application
version: 0.1.0
dependencies:
  - name: user-service
    version: 0.1.0
    repository: "file://../charts/user-service"
  # ... 其余 5 个同理
```

**面试叙事**：`helm list` 看 6 个独立 release；`helm upgrade user-service` 独立发布；`helm install smart-invest` 一键部署全家。

### 4.2 Kustomize 多环境

- `base/`：引用 helm render 出的 base 清单（或直接作为 Kustomize base）
- `overlays/dev|uat|prd/`：用 `patchesStrategicMerge` 调整副本数/资源限制/镜像 tag
- 面试叙事：helm 管"模板与发布"，kustomize 管"环境差异"，两者职责互补

### 4.3 Terraform 管 K3S（学习资料）

- 用 `kubernetes` + `helm` provider 声明式管理 K3S 上所有资源
- 与 AWS EKS 版对比讲解：同一套 Terraform 心智，provider 换成点不同的集群
- 明确标注为"学习用"，不作为主部署路径

## 5. CI/CD（GitHub Actions 全自动）

```
push → workflows/ci-cd.yml
  ├─ 检测变更服务（paths-filter）
  ├─ 后端: mvn package → docker build → docker push (Docker Hub)
  ├─ 前端: npm ci → vite build → nginx docker build → docker push
  └─ 部署: SSH 到 ASUS-Ubuntu
         ├─ 拉取 kubeconfig
         ├─ helm dep update && helm upgrade --install smart-invest ./umbrella
         └─ 健康检查（kubectl rollout status）
```

- 镜像 tag：`git sha` 或版本号，保证可追溯
- Docker Hub 凭据、服务器 SSH 密钥存 GitHub Secrets
- 面试叙事：代码 push 即部署，制品可追溯回源码 commit

## 6. 监控与可观测性

- **Prometheus + Grafana**：Helm 部署（`prometheus-community/kube-prometheus-stack` 或精简版）
- **微服务指标**：`micrometer-registry-prometheus`，暴露 `/actuator/prometheus`
- **RabbitMQ**：启用官方 prometheus 插件 + exporter，采集队列指标
- **Grafana 预置面板**：
  - JVM（堆/GC/线程）
  - HTTP（QPS/延迟/错误率）
  - 服务间调用
  - RabbitMQ（队列积压/生产/消费速率）
- **K8S 自身指标**：kube-prometheus 自带的 node/controller 面板
- 面试叙事：从架构图的 CloudWatch→Grafana 的心智迁移

## 10. 明确不做（YAGNI）

- 不做 Istio 服务网格（单节点，演示用 REST + 服务发现即可）
- 不做 AWS 专有服务接入（SES 邮件 → 日志打印替代；CloudWatch → Grafana）
- 不做多环境真实隔离（Kustomize overlay 结构保留，但 dev/uat/prd 共用同一 K3S）
- 不做 HPA 自动扩缩（保留 HPA manifest，但单节点默认不启用，避免资源争抢）
- 不做两地三中心/容灾（面试口头讲即可，代码不实现）
