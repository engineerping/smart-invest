Spring 的事务传播机制（Transaction Propagation），如果跳出代码，站在架构设计的角度去看，它其实是一套“处理人际关系”的哲学。

那么它到底在关注什么、要解决什么问题呢

---

## 一、 事务传播行为到底在关注什么？

一句话总结：**它关注的是“当一个带事务的方法，调用了另一个带事务的方法时，它们俩的事务边界该怎么算？”**

想象一下：方法 A 启动了事务，执行到一半，调用了方法 B。方法 B 身上也写着要事务。这时候，方法 B 就要做决策了：

* 我是直接加入 A 的家庭（合并成一个事务）？
* 还是我自己出去单干（自立门户，各不相干）？
* 还是我依附于 A，但给自己留个退路（嵌套事务）？

这就是传播行为关注的核心：**多个有事务的方法嵌套调用时，事务的生命周期（提交、回滚、隔离）如何跨方法进行传递和合并。**

---

## 二、 事务传播机制要解决什么问题？

它解决的核心问题是：**代码复用与业务原子性之间的冲突。**

在开发中，为了复用代码，我们习惯把业务拆得很细。

* `UserService.register()`：用户注册（需要事务）。
* `LogService.log()`：记录系统日志（需要事务）。

现在有一个高级业务 `AdminService.createAdmin()`，它需要先调用 `register()` 注册用户，再调用 `log()` 记录日志。

这时候冲突就来了：

1. **对于 `log()` 自身来说**：平时别人单独调用我时，我得自己开个事务，保证日志能存进去。
2. **对于 `createAdmin()` 来说**：日志记不记录成功不重要，但如果用户注册失败了，整个操作得回滚。或者反过来，如果日志记失败了，不能影响用户注册。

**传播机制就是为了解决这种“各怀鬼胎”的业务场景。** 它允许你在写 `log()` 方法时，定义好：“不管谁调用我，我该如何处理我跟他的事务关系”。从而让你可以**任意组合零散的方法，而不会破坏业务的数据一致性**。

---

## 三、 是因为使用了 Spring 框架才产生的问题吗？

**不是！绝对不是！**
这是 **多业务逻辑嵌套时，底层数据库连接（Connection）管理** 的固有矛盾。即使你不用 Spring，纯写 JDBC，你也逃不掉这个问题。

### 1. 纯 JDBC 时代的痛苦

在没有 Spring 之前，我们要控制事务，必须手动拿到 `Connection` 对象，然后 `conn.setAutoCommit(false)`。

如果你想让方法 A 和方法 B 在同一个事务里，你必须**显式地把 `Connection` 对象当作参数传给方法 B**：

```java
public void methodA() {
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);

    insertUser(conn, user); // 必须传 conn
    methodB(conn);          // 必须把同一个 conn 传给 B，才能保证在同一个事务里

    conn.commit();
}
```

* **问题来了**：如果方法 B 想要“不管 A 成功与否，B 都必须单独成功”（即 `REQUIRES_NEW` 的场景），你怎么写？你必须在 B 里面再去申领一个新的 `Connection`，然后手动提交。
* 代码里充斥着大量的 `Connection` 传递、`try-catch-finally`、手动 `commit` 和 `rollback`。代码极其臃肿，业务逻辑被严重污染。

### 2. Spring 做了什么？

Spring 并不是制造了这个问题，而是**用了一种优雅的方式（AOP 和 ThreadLocal）帮你解决了这个问题**。

Spring 引入了 `TransactionManager`（事务管理器）。当它发现方法嵌套调用时，它在后台帮你默默地管理着不同的 `Connection`（或者在同一个 Connection 上设置 `Savepoint`）。
你不需要再满世界传递 `Connection` 了，你只需要在方法上贴个 `@Transactional(propagation = ...)` 的标签，告诉 Spring 你的诉求，剩下的脏活累活（挂起连接、新建连接、标记回滚）都由 Spring 的 AOP 拦截器帮你搞定。

## 四、 核心：嵌套事务（NESTED）是如何工作的？

正如你描述的，`NESTED` 的核心是数据库的 **Savepoint（保存点）**。它是最让人迷惑、但也最强大的机制。我们通过一个具体的场景来看它是如何工作的。

### 场景设定

* 外层方法：`orderService.placeOrder()`（下单，扣余额）
* 内层方法：`couponService.rollbackCoupon()`（回滚优惠券，非核心业务，**标记为 NESTED**）

```java
@Transactional(propagation = Propagation.REQUIRED)
public void placeOrder() {
    // 1. 扣减用户余额
    deductBalance(); 

    try {
        // 2. 调用内层嵌套事务：退还优惠券
        couponService.rollbackCoupon(); 
    } catch (Exception e) {
        // 捕获内层异常，防止外层跟着回滚
        System.out.println("优惠券退还失败，但订单继续执行");
    }
    // 3. 扣减库存
    deductStock();
}

@Transactional(propagation = Propagation.NESTED)
public void rollbackCoupon() {
    // 执行退券 SQL
}
```

### 运行时的底层工作原理

1. **外层启动**：进入 `placeOrder`，Spring 发现当前没有事务，于是获取一个连接 `Conn_1`，开启事务（相当于执行 `BEGIN`）。
2. **执行外层 SQL**：执行扣减余额。
3. **进入内层**：准备执行 `rollbackCoupon`。Spring 发现当前**已经存在**一个事务（`Conn_1`），并且内层是 `NESTED`。
4. **创建保存点**：Spring **不会**去拿新的连接，也不会开启新事务，而是利用现有的 `Conn_1`，在数据库里设定一个保存点：`SAVEPOINT savepoint_coupon;`
5. **执行内层 SQL**：执行退券 SQL。

#### 情况 A：内层失败了（退券报错）

* 内层方法抛出异常。
* Spring 的事务拦截器捕获到异常，它**不会**把整个 `Conn_1` 标记为回滚，而是下达指令：`ROLLBACK TO savepoint_coupon;`（数据回滚到发券前的状态，扣减余额的记录依然安全）。
* 在外层方法中，因为我们用了 `try-catch` 抓住了这个异常，外层代码继续往下走，成功扣减库存。
* **最终结果**：外层成功提交，内层完美回滚。

#### 情况 B：内层成功，外层后面失败了（扣库存报错）

* 内层退券成功，此时没有触发 `ROLLBACK TO`。
* 代码回到外层，执行 `deductStock()`（扣库存）时突然报错。
* 外层事务拦截器捕获异常，由于它是主事务，它直接下达终极指令：`ROLLBACK;`
* **最终结果**：由于是整条连接的回滚，**内层不管之前多成功，都会被连坐，一起烟消云散**。

## 总结

| 传播行为                         | 关注的点                    | 解决的问题                                | 核心底层机制                                    |
| ---------------------------- | ----------------------- | ------------------------------------ | ----------------------------------------- |
| **REQUIRED** <br></br>*(默认)* | “我们要同生共死”               | 默认的大多数业务场景，确保整套操作的原子性。               | 共享同一个 `Connection`。                       |
| **REQUIRES_NEW**             | “你是你，我是我，互不干扰”          | 比如不管业务成功与否，日志/审计信息都必须记录成功。           | 挂起当前 `Connection`，开启**全新**的 `Connection`。 |
| **NESTED**                   | “我是你的附庸，你死我必死，但我死你可以保帅” | 核心主业不能受次要副业的影响（如发邮件、送积分、退券失败不能影响下单）。 | 在**同一个** `Connection` 中使用 `SAVEPOINT`。    |

---

除了最常用的 `REQUIRED`、`REQUIRES_NEW` 和 `NESTED` 之外，Spring 还提供了另外 4 种事务传播行为。它们虽然不常用，但在某些特定的高并发、架构解耦或严格校验的场景下，能起到奇效。

我们同样用一张表把它们理清楚：

### Spring 其余 4 种事务传播行为一览

| 传播行为              | 关注的点                    | 解决的问题                                           | 核心底层机制                                                |
| ----------------- | ----------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| **SUPPORTS**      | “有事务我就混一下，没事务我也能裸奔”     | 主要用于纯查询操作。既能单独高效运行，又能融入外层事务以读取未提交的数据。           | 有事务则加入（共享 `Connection`）；无事务则以普通 JDBC 状态运行。            |
| **NOT_SUPPORTED** | “不管你有没有事务，反正我不要，而且别拖累我” | 解决耗时非核心操作（如发大邮件、调远程外部 API）长时间霸占数据库连接导致连接池干涸的问题。 | 若有事务，先**挂起**当前 `Connection`，释放或暂存，以非事务状态（无连接或用完即还）运行。 |
| **MANDATORY**     | “我是一个寄生虫，谁调我谁就必须带上事务”   | 核心敏感操作（如钱包扣款）的安全防御，防止被开发人员在无事务的环境下误调用而导致账目错乱。   | 检查当前线程是否存在事务：存在则加入 `Connection`；不存在直接**抛出异常**拒绝执行。    |
| **NEVER**         | “我有强烈的事务洁癖，离事务远一点”      | 严格禁止在事务上下文中运行的特定业务控制（如某些基础数据初始化、或防止死锁的特定逻辑）。    | 检查当前线程是否存在事务：存在则直接**抛出异常**；不存在则以非事务状态运行。              |

### 举个例子，加深理解：

为了让你更有体感，我们来看两个实际的小案例：

#### 1. 为什么会有 `NOT_SUPPORTED`？

想象一下，用户下单（`REQUIRED`）成功后，需要调用一个 `sendSmsEmail()` 方法去发送通知邮件。
发送邮件是一个网络 I/O 操作，可能需要耗时 3 秒钟。

* 如果你用 `REQUIRED`（默认）：发送邮件的 3 秒钟内，数据库连接一直被这个线程占着，无法释放。高并发下，数据库连接池瞬间就干涸了。
* 如果你用 `NOT_SUPPORTED`：进入该方法时，Spring 会把外层的事务**挂起**（腾出数据库连接），等邮件发送完（不管是成功还是超时失败），再恢复外层事务。这样可以极大节省数据库连接资源。

#### 2. 为什么会有 `MANDATORY`？

在一个大型电商系统中，钱包扣款方法 `walletService.decreaseMoney()` 极其核心，绝对不允许被单存、盲目地调用，必须依附于“创建订单”或者“充值流水”的整体事务中。
把该方法设为 `MANDATORY`，就像加了一把安全锁：任何新来的开发仔如果不小心在业务外层直接调用了扣款，程序在运行到这里时会**直接崩溃报错**，从而避免了“由于没有事务包裹而导致账目对不齐”的灾难。

### 💡 终极穿透理解

通过这张表，你会发现 Spring 事务传播机制的底层，说白了就是在玩两个东西：

1. **对 `Connection`（数据库连接）的操控**：是复用它、新建它、挂起它，还是不用它。
2. **对线程状态（ThreadLocal）的检查**：在进入方法前，探查一下当前线程有没有绑定事务资源，然后根据策略决定是“加入”、“拒绝”还是“报错”。

掌握了这两点，不管面对多么复杂的业务嵌套，你都能一眼看穿它的事务走向。
